Proposed — three variants

One ramp, two themes

The dark buttons used to pick their own colours, which is why they felt unrelated. Both themes now walk the same indigo ramp, by the same rule: the default is the theme's maximum-contrast fill, hover steps onto the ramp, pressed goes one step further. Six of these eight steps already exist in the build — only #8F86FF and #6E66FF are new, and they get names rather than being invented per button.

Decided and shipped

#7F849F is the secondary border, and the whole system is live in both builds. The two notes below record why.

Two changes you'll see immediately

The secondary border gets darker. Today's #D2D5EA is 1.45:1 against white — decorative weight. WCAG 1.4.11 asks for 3:1 on the boundary that identifies a control, and #7F849F is the lightest value that clears it on all three light surfaces. It is a visible change in character; if you'd rather keep the hairline, the counter-argument is that these buttons also have a text label and a filled shape, so the border isn't the only affordance. Your call.

The focus ring changes colour on dark. Indigo on the business card is 2.37:1 — effectively invisible. Lilac #A79BFF takes it to 7.87:1.

So pressed no longer leans on its fill. It now carries three cues at once: the fill steps down the ramp, the button shifts 1px down, and it gains an inset top shadow — a shading cue that survives greyscale completely. Rendered with all colour stripped out, the pressed button's top edge measures 44.8 against hover's 65.0 on a 0–255 scale — a visible lip that has nothing to do with hue. Try the live buttons above.

  • The carousel dots mark the active slide by width — 22px versus 9px — not by colour, plus aria-selected.
  • The open pricing tier expands to reveal its content, so the dark fill is a reinforcement rather than the signal, plus aria-expanded.
  • There are no inline links inside body copy, so nothing depends on link colour to be recognised as a link.
  • The four feature panels do collapse under achromatopsia — ΔE between them drops to 1–9, so they read as four near-identical greys. Nothing is lost, because each panel is labelled in words and the running order is the sequence. Worth knowing if you ever plan to carry meaning in those hues.

Verdict

Colour vision: clear. Tap targets: clear, with the two fixes applied to the live builds. The one thing I changed in the proposal as a result is the pressed state, which now has a shading cue so it never depends on hue.

Token problems

  • --tip-stroke: #484D6B is an exact duplicate of --muted. Two names, one colour, so changing one silently desyncs the other.
  • --ground meant two different colours until this pass — now one, #EAECFA, with --wash #F4F5FC beneath it.
  • Twelve UI colours are written as literals with no token at all: the panel captions, the business text colours, the pricing tag and the card gradients.
  • Desktop declares --wash, --indigo-hi, --indigo-soft, --tip-stroke; mobile declares --tag and three --biz-* tokens. Neither set is complete.

How this stays true

The system is not a document that pages are asked to follow — it is a file they are built from, and a check that rejects them if they drift.

FileWhat it does
_system/system.cssThe law. Tokens, the indigo ramp, and every button variant and state. The only place these values exist.
_system/apply.pyInjects the law into each page between markers, deletes the local button rules it supersedes, rewires markup onto the system classes, and folds duplicate colours onto their canonical token.
_system/check.mjsDrives headless Chrome over both views, forcing hover, focus and active on all 43 controls, and reports every violation.
06-responsive/build.pyRuns the check on every build and exits non-zero if anything fails. A page that breaks the system does not ship.

The five laws

  1. Every interactive control is at least 24×24, hit area included.
  2. Every interactive control has a visible hover change.
  3. Every interactive control has a focus ring — indigo-600 on light, indigo-200 on dark.
  4. Every .btn resolves to its variant's token values. No local overrides.
  5. No colour outside the palette may appear on a system component.

Proof it bites

I added style="background:#B22222" to one button and rebuilt. The build stopped:

HOVER   desktop · "Start project" has no hover change
TOKEN   btn-primary backgroundColor is rgb(178, 34, 34), law says rgb(12, 16, 36)
TOKEN   btn-primary hover backgroundColor is rgb(178, 34, 34), law says rgb(58, 52, 214)
PALETTE   backgroundColor rgb(178, 34, 34) is not in the palette
BUILD REJECTED — exit 1

Changing the law is still possible, and that is the point: you edit system.css, and every page picks it up on the next build. What you cannot do is change one button in one page and have it survive.

Where the rollout deviates from the old pixels

Buttons settled on the system's sizes, so a few grew: the composer's Start project went 41 → 44px tall, the panel arrows 34 → 40px, and the mobile Join Envoy for Business 14 → 15px. The pricing tier's dark fill and the business card now share one purple, and text on dark is pure white rather than #EDECF7. Page heights are unchanged: 3407px desktop, 3135px mobile.
